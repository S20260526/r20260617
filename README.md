# Описание проекта

Распределённая трёхзвенная система для обработки бинарных данных.

## Архитектура

Система состоит из сервисов трёх типов: front, worker, janitor, взаимодействующих через очереди и хранилища. Технически любой из этих сервисов может существовать в нескольких экземплярах.

Сценарий обработки:
1. внешний клиент отправляет HTTP `POST /` с бинарным телом сервису **front**.
2. сервис front сохраняет бинарные данные в объектное хранилище **SeaWeedFS**
3. сервис front формирует заказ — JSON с меткой времени и идентификатором данных в хранилище — и помещает его в рабочую очередь **RabbitMQ**
4. сервис worker извлекает заказ, загружает blob из SeaWeedFS и отправляет его данные в сопроцес
5. По результату работы сопроцесса:
     - при результате `YES` — worker записывает событие в **PostgreSQL**
     - при результате `NO` — worker удаляет blob из хранилища
     - при результате `FAIL` — worker отклоняет сообщение, возвращая его в очередь
6. Сообщения, не прошедшие обработку, попадают в **DLQ**. Сервис janitor потребляет сообщения из DLQ и удаляет связанные с ними данные из хранилища.

### Сервисы

| Сервис | Пакет | Назначение |
|--------|---------|-----------------------------------------------------------|
| **front** | `cmd/front` | Принимает `POST /` с бинарными данными и сохраняет их в хранилище. |
| **worker** | `cmd/worker` | Загружает данные из хранилища, и отправляет данные в сопроцесс через gRPC |
| **janitor** | `cmd/janitor` | Потребитель очереди DLQ — удаляет осиротевшие blob из хранилища. |

### Хранилища

| Компонент | Назначение |
|-----------|----------------------------------------------------------------------------|
| **SeaWeedFS** | Объектное хранилище. Для упрощения работы используется (мало)документированный REST-API |
| **PostgreSQL** | Реестр событий. Принимает `INSERT` в таблицу с полями `t` (метка времени) и `id` (Blob ID) |
| **RabbitMQ** | Брокер сообщений. |
| **etcd** | Конфигурация. Сервисы отслеживают изменения ключей с префиксом `root.*` и при необходимости переинициализируются. |

### Сопроцесс

Сервис worker делегирует обработку данных сопроцессу, временем жизни которого управляет сам сервис worker. Результатом выполнения может быть:

| Результат | Действие |
|-----------|--------------------------------------|
| `YES` | Регистрация события в PostgreSQL. |
| `NO` | Удаление blob из хранилища. |
| `FAIL` | Отклонение сообщения (возврат в очередь). |

Сопроцесс представляет собой скрипт написанный на Python 3, что вполне типично для задач ML и CV, решаемых специалистами-"предметниками".

### Конфигурация

Все сервисы используют единую схему конфигурации, хранящуюся в etcd. Определены следующие параметры:

| Ключ | Значение по умолчанию | Описание |
|----------------------|--------------------|----------------------------------------------|
| `root.input.port` | `8089` | Порт HTTP сервера front |
| `root.storage` | `localhost:9333` | Адрес хоста и порт REST-API SeaWeedFS |
| `root.pushing.host` | `localhost:5672` | Адрес хоста и порт подключения RabbitMQ для сервиса front |
| `root.pushing.queue` | `working` | Имя очереди RabbitMQ для сервиса front |
| `root.pulling.host` | `localhost:5672` | Адреса хостов и порты подключения RabbitMQ для сервисов worker и janitor (через запятую для нескольких узлов) |
| `root.pulling.queue` | `working` | Имя очереди RabbitMQ для сервисов worker |
| `root.pulling.dlq` | `DLQ` | Имя очереди DLQ для сервиса janitor |
| `root.pulling.retry.t | `1s` | Время ожидания после неудачного вытягивания данных из RabbitMQ для сервисов worker и janitor |
| `root.script.file` | `/dev/null/main.py` | Путь к Python-скрипту сопроцесса |
| `root.registrator.driver` | `postgres` | Имя драйвера базы данных |
| `root.registrator.dsn` | `postgres://...` | DSN драйвера базы данных |
| `root.registrator.table` | `events` | Имя используемой для хранения событий таблицы базы данных, должно удовлетворять правилам ANSI SQL |

## Структура

Проект использует Go workspace с несколькими модулями.

```
├── cmd/
│   ├── front/           # HTTP-сервер — принимает POST /
│   ├── worker/          # Основной цикл обработки
│   └── janitor/         # Очистка хранилища и DLQ
├── internal/
│   ├── app/             # Основные интерфейсы и бизнес-логика (Front, Worker, Janitor, Order, Event)
│   │   ├── msgqueue/    # Абстракция очередей: Pusher, Puller
│   │   ├── front.go
│   │   ├── worker.go
│   │   ├── janitor.go
│   │   ├── coprocess.go
│   │   ├── storage.go
│   │   ├── order.go
│   │   ├── event.go
│   │   └── configuration.go
│   ├── grpcipc/         # Определение Protobuf и сгенерированный код для gRPC-взаимодействия
│   │    └── proto/
│   │          └──ipc.proto
│   └── infra/           # Инфраструктурные адаптеры: RabbitMQ, SeaWeedFS, PostgreSQL, Prometheus, etcd, сопроцесс
└──  testbench/          # Отладочные примеры использовавшиеся для интерактивной разработки компонентов системы
```

## Тестирование и сборка

```bash
# Запустить все тесты в workspace
go test ./internal/app ./internal/app/msgqueue ./internal/infra
```

Для сборки помимо Go необходим также пакет Python3 grpc\_tools (в Debian ставится из стандартного репозитория пакетами python3-grpcio, python3-grpc-tools)

```bash

# Сгенерировать код для gRPC-взаимодействия
make -C internal/grpcipc

# Собрать все три сервиса
go build ./cmd/front
go build ./cmd/worker
go build ./cmd/janitor
```
